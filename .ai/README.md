# AIハーネス導入ガイド

このディレクトリは、`AGENTS.md` の共通行動規範を補足する。プロジェクト知識の本体は人間も参照する `README.md` と `docs/` に置き、ここへ重複して詰め込まない。

## 導入手順

1. 未配置の `AGENTS.md` と `.ai/` を配置する（テンプレート自身の保守taskは除く）。既存ファイルがある場合は、後述の導入・更新手順に従って差分を統合する。
2. `.ai/project.md` に、AI作業へ影響するプロジェクト固有ルールだけを、実際のコード、設定、テスト、READMEから確認して記入する。
3. 詳しい仕様や設計は `README.md` または `docs/` に記載し、`.ai/project.md` から必要に応じて参照する。
4. バージョン管理が必要な時点で、`common.md` の「バージョンと変更履歴」に従い、導入先の開始値・保存先・互換性の判断対象を設定する。テンプレート原本の値や履歴は持ち込まない。
5. 軽微な修正を含む個別の実装依頼では、AIが先に必要なtaskを用意する。ユーザーが既存taskを指定してもよい。採番・承認は `common.md` に従う。
6. 導入後、AIが既存のマニフェスト、スクリプト、CI設定、README、テストから検証手段を発見できることを確認する。

推測した仕様や、まだ導入していないツールを確定事項として記載しないこと。秘密値、個人情報、実運用データはこのディレクトリへ保存しないこと。

## ファイルの役割

- `../AGENTS.md`: AIが最初に読む入口と指示の優先順位
- リポジトリ直下の `VERSION`・`CHANGELOG.md`: 導入先のバージョン正本と変更履歴（既存配置がある場合は維持）
- `common.md`: プロジェクトを問わず共通する調査・変更・検証・報告ルール
- `project.md`: AIの変更判断へ直接影響する、最小限のプロジェクト固有ルール
- `guides/`: 要求整理、設計、実装、テスト、レビューの再利用可能なフェーズ別手順
- `tasks/`: 機能追加や変更ごとの指示と、実装後の試験・修正で確定した内容を残す個別タスク文書

`guides/` の全ファイルを毎回読む必要はない。依頼に関係するファイルだけを読み、複数フェーズにまたがる場合は該当するものを組み合わせる。

`tasks/` の完全なtask IDは一意な識別子として扱い、親子関係や依存関係は各タスク文書に明記する。実装後の人手試験で修正が必要になった場合は、その内容を該当taskへ反映してからAIへ修正を依頼する。完了後も有効な仕様や設計は `README.md` または `docs/` に反映し、タスク文書だけを恒久的な仕様の根拠にしない。

最小構成から始めたい場合は、`.ai/common.md` の必要な要点と短い `Project Specific Rules` を `AGENTS.md` に統合する。その場合は、存在しない `.ai/common.md`、`.ai/project.md`、`.ai/guides/`、`.ai/tasks/` を必須とする記述も、実際の構成に合わせて削除または調整する。現在の `AGENTS.md` だけをそのままコピーして使用しない。このテンプレートは、役割を分けて保守したい場合の展開形である。

## 要件定義から始める場合

`guides/01-requirements.md` に従って `docs/requirements.md` を作成・更新する。この作業だけなら専用taskは不要。
READMEは概要、requirementsは現在の要件、taskは個別作業の指示と結果として役割を分ける。
要件に合意した後も、次の作業は依頼の範囲に従う。実装等が依頼された段階で、対象要件IDを参照するtaskを用意する。

## 新規・既存の両方で使う

同じハーネスを使い、AIが依頼と作業対象の実態から進め方を判断する。ユーザーによるモード指定は不要。既存部分は契約と互換性を守り、未実装部分は必要十分な初期設計・構成・検証手段を用意し、混在する場合は接続部分も確認する。未決・未整備の事項はその状態を明記し、決定や検証後にproject.mdへ反映する。

実装依頼には必要なtaskの作成と進捗・検証結果の記録を含む。要求や受け入れ条件をAIが勝手に変更する権限は含まない。

## 既存プロジェクトへの導入・ハーネスの更新

テンプレートの更新を他プロジェクトへ自動適用せず、ユーザーが依頼した範囲で次に従う。

- 規範文書は現在有効な本文へ統合し、日付別の追記や旧指示との併存を避ける。経緯はtask・Git履歴などへ分離する。
- 既存ファイルは差分統合し、固有ルール、保護対象、要件正本と参照先、既存変更を保持する。一括上書きせず、ファイルが未配置の場合だけ新規配置する。
- 反映作業ごとに導入先で新しいtaskを作り、過去taskは変更しない。テンプレート自身の保守taskや未適用taskは持ち込まない。
- アプリのロジック・実行設定の修正や、既存試験結果の移動は更新に含めず、別の作業として扱う。
- 取得元・適用元コミット・独自調整を導入記録に残し、リンクと指示の整合、既存内容の保持、差分を検証する。変更内容・検証結果・未確認事項を新taskに記録し、リポジトリごとに一覧で報告する。

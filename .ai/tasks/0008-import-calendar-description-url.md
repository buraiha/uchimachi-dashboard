# Googleカレンダーの説明欄から予定URL・メモを取り込む

- Status: completed
- Depends on: none

## 目的と要求

Googleカレンダーの予定取得時に、各予定のメモ（説明欄・`description`）からURLを抽出し、ダッシュボード側の予定URLとして利用し、URLらしい文字列と空行を除いた本文も予定メモへ取り込む。

2026-09-17のユーザー指示「task0008を実装してください。テストまで」に基づき、以下の仕様で実装する。

## 実装前の状態

- `src/main.rs` の `GoogleCalendarEvent` は説明欄を保持していない。
- `fetch_calendar_events` は、`calendar_id` と `event_id` に対応するSQLiteの予定メモ・URLを `event_memo`・`event_url` に反映する。
- ダッシュボードの関連URLは `【リンク】` として表示され、`/events/manage` で手入力・保存できる。
- Googleカレンダーの予定自体への `htmlLink` と、今回抽出する関連ページのURLは用途が異なる。

## 確定仕様

今回の実装指示により以下の提案を採用する。

- 予定の `description` を取得し、本文中のHTTP／HTTPSのURLを抽出する。プレーンテキストのURLとHTMLのリンク（`a` 要素の `href`）を対象とする。
- 複数ある場合は、説明欄の出現順で最初の有効なURLを1件採用する。HTMLのリンクは表示文字列ではなくリンク先を使用する。
- 既存の手入力URLが空でない場合は、それを優先して保持する。空の場合に抽出URLを `event_url` として利用する。
- 取得時の反映を基本とし、取得だけでSQLiteへ自動保存・上書きしない。説明欄のURLの変更・削除は、次回取得時に反映する。
- `/events/manage` でも採用したURLを確認・編集できるようにし、保存した場合は既存の手入力URLとして扱う。
- 説明欄がない、空、または有効なURLを含まない場合、手入力URLがなければ関連リンクを表示しない。Googleカレンダーの `htmlLink` を代用しない。
- 説明欄の本文も予定メモへ取り込む。本文中のURLらしい文字列は、最初のURLを含めすべて除去し、空行（空白だけの行とURL除去で空になった行を含む）も除く。
- 元のGoogle説明欄を変更しない。保存済みの手入力メモがある場合は優先し、空の場合だけ説明欄の本文を使う。取得のみではSQLiteへ保存しない。メモとURLは独立に優先順位を判定する。
- ユーザー指定により既存の160文字上限を維持する。URL・空行の除去後に先頭160文字を採用する（改行も文字数に含む）。
- HTMLは本文だけをテキスト化する。br・段落・リスト等の区切りは改行に変換し、コメント・script/styleとタグ属性は本文に含めない。リンクの通常のラベル文字列は残し、URLの形のラベルは除く。
- URLらしい文字列の除去は、HTTP/HTTPSに限らず `scheme://`、`www.`、`mailto:` を対象とし、不正URLや長さ超過の候補も除去する。URL欄に使うのは従来どおり最初の有効なHTTP/HTTPSの1件だけで、2件目以降は採用しない。

## 守るべき仕様と制約

- 予定は `calendar_id` と `event_id` の組み合わせで識別し、別カレンダーの同一IDの予定と混同しない。
- 抽出URLにも既存の `normalize_event_url_input` 相当の検証を適用し、HTTP／HTTPSのみ、2048文字以内とする。不正な候補があっても予定一覧全体の取得を失敗させない。
- HTMLの説明欄をそのまま画面に埋め込まない。属性値や表示値は既存のHTMLエスケープを通す。
- 抽出したリンク先へサーバーからアクセスしない。
- `calendar.readonly`、認証保護、表示件数、日時処理、手入力メモの保存仕様を維持する。
- 依存関係やSQLiteスキーマの変更は前提にしない。必要性が判明した場合は理由と影響を整理する。

## 受け入れ条件

以下を受け入れ条件とする。

1. 説明欄に有効なURLがあり手入力URLがない予定では、抽出したURLがダッシュボードの `【リンク】` と予定メモ設定のURL欄に反映される。
2. プレーンテキストとHTMLリンクの両方を扱え、クエリ文字列やHTMLエンティティを含むリンク先を壊さない。
3. 複数URL、説明欄欠落、空欄、不正URL、許可外スキーム、長すぎるURLの挙動が仕様どおりである。
4. 既存の手入力URL・メモは取得処理で上書きされず、別の予定へURLが混入しない。
5. 手入力URLがない場合、説明欄のURLの変更・削除が次回取得に反映される。取得だけではSQLiteへの書き込みが発生しない。
6. 予定メモ設定でのURL保存・空欄保存が確定仕様どおり動作し、既存の保存結果通知も維持される。
7. 外部由来のHTMLやURLが安全に扱われ、Google側のデータやOAuth scopeが変更されない。
8. 説明欄から取り込んだメモにURLらしい文字列や空行が残らず、URLが複数あっても最初の有効なURLだけをURL欄に表示する。
9. 取り込みメモの表示・保存・空欄保存・再取得と、保存済みメモの優先を検証する。

## URL境界と保存時の確定動作

- 複数URLは説明欄の出現順で最初の有効な1件を使用する。HTMLのa要素はhrefを評価し、リンク表示文字列は候補にしない。他のタグの属性、コメント、script/styleの内容は対象外。
- プレーンURLは空白、引用符、山括弧、日本語の句読点・括弧で区切る。末尾のASCII句読点（.,;!）と対応する開き括弧のない閉じ括弧を除く。URL内の対応する丸括弧とクエリ文字列は保持する。曖昧な末尾句読点を含むURLはhrefまたはパーセントエンコードを使う。
- HTMLエンティティは基本的な名前付き参照（amp/quot/apos/lt/gt/nbsp、colon/sol）と10進・16進の数値文字参照を1回だけ復号する。未知の参照は保持する。
- 手入力URL優先。取得時はSQLiteへ保存しない。URL欄を保存すると表示中の抽出URLも手入力URLとなる。空欄保存すると手入力URLを解除し、次回取得で説明欄のURLを再び採用する。非同期保存直後の入力欄はそのまま保持する。

# Individual Task Documents

このディレクトリには、機能追加やデータ構造の変更など、ひとまとまりの開発内容ごとの指示書を置く。
実装・修正の依頼には、対象範囲で必要なtaskの作成と、Status・実施結果・検証結果の更新を含む。文書更新のためだけに再承認を求めない。要求・対象範囲・受け入れ条件の実質的な変更や、未指定taskの変更は別途ユーザーの指示に従う。調査・レビューだけの依頼では、task更新が依頼されていない限り文書を変更しない。

## 要件定義書との関係

要件定義書の作成・更新だけの依頼では、`docs/requirements.md` を直接管理し、専用taskは必須にしない。詳細は [要件定義ガイド](../guides/01-requirements.md) を参照する。
実装・設定変更・ハーネス変更等の個別作業にはtaskを用意する。要件定義とそれらが同時に依頼された場合は、その作業範囲をtaskに記載する。
各実装taskは対象要件IDと正本の該当箇所を参照し、要件全文の複製を避ける。要件変更が進行中taskに影響する場合は、ユーザーの依頼範囲でtaskも更新し、不整合を残さない。
既存の要件定義taskは過去の記録であり、正本ではない。削除は別途依頼がある場合に行う。

## 作業依頼と実装後の更新

軽微な修正でも、実装前にtaskを用意する。ユーザーが既存taskを指定する方法と、実装依頼を受けたAIが先にtaskを作成する方法のどちらでもよい。作成したtaskは現在の依頼範囲を記録し、文書の作成自体を実装承認とは扱わない。

最初の task 文書は、目的、期待する結果、守るべき点など、実装に必要な簡易の指示だけを記載した状態でもよい。task 文書は完全な実装手順書ではないため、既存実装を調査すれば判断できる実現方法や細部には曖昧さを残してよい。

実装後は人間が試験し、必要な修正があれば、原則としてその内容を該当する task 文書へ追記してから、対象ファイルを明示して AI に修正を依頼する。人間が文書を直接更新する代わりに、AI へ「試験結果を task 文書へ反映してから修正する」よう一度に依頼してもよい。

修正を重ねて動作や仕様が固まったら、AI に task 文書の更新を依頼し、試験で確定した要求、修正内容、受け入れ条件などを反映する。

## 命名

新しい独立taskのファイル名は `4桁の連番-開発内容.md` とし、開発内容には英小文字の kebab-case を使用する。親taskを分割した子taskは、`親taskID_4桁の子番号-開発内容.md` としてよい。

```text
0001-add-authentication.md
0002-add-user-pricing-table.md
0003-add-pricing-settings-ui.md
0040_0010-add-auth-data.md
```

task IDは、独立taskでは先頭の4桁、子taskでは親task IDと子番号を結合した部分とし、完全なIDが一意になるようにする。たとえば `0040_0010-add-auth-data.md` のtask IDは `0040_0010` である。

実行順序を番号だけで判断せず、依存するtaskがある場合は本文の `Depends on` に完全なtask IDを明記する。

既存の日本語名、アンダースコア形式、子番号形式など、以前の運用で作成されたtask文書は歴史的な記録としてそのまま維持し、新しい命名規則へ合わせるためだけに改名しない。

## 試験結果の保存と確認

- 新しい試験結果は `.ai/tasks/<完全なtask ID>/test-results.md` に保存し、task本文からリンクする。ログ・画像も同じフォルダに置く。タスク文書の配置は変えない。
- 自動・人手試験を区別し、日時、対象版、環境、コマンド・手順、期待値と実際の結果、合否、未実施の理由を記録する。人手試験は結果の提供元も記す。再試験は過去の結果を残して追記する。
- AIは再開時と完了前に結果と必要な証跡を読み、現在の変更と受け入れ条件に照合する。欠落・古い結果・未実施は未確認とし、合格や完了を推測しない。
- 秘密情報・個人情報・実運用データを保存しない。既存結果は移動せず参照する。継続利用する試験手順・仕様は `docs/` に置く。

## 記載項目

以下は標準的な構成例であり、すべての項目を必須とはしない。軽微な修正では、必要な項目だけを使った短い task 文書でよい。

```markdown
# <タスク名>

- Status: proposed | approved | in-progress | implemented | completed
- Depends on: none | <タスクID>

## 目的と要求

## 変更対象

## 対象外

## 守るべき仕様と制約

## 受け入れ条件

## バージョン提案と承認

リリース対象のロジック変更の場合のみ、現在値、次期バージョン、理由、互換性への影響、ユーザーの承認と対象範囲、リリース待ち／完了等の状態を記載する。採番は試験完了後・リリース前のコミット直前、バージョニング作業の完了は、リリース成功後の履歴確定・コミット・版タグ付与・対象ブランチとタグのpush確認後とする。taskの実装・試験完了とは区別する。文書整備・調査・記録等だけのtaskでは本項目は不要。

## 想定する検証
```

実装後の内容を残す場合は、必要に応じて `追加・修正指示`、`実施結果`、`人手試験結果` などを追記する。当初の指示と後から確定した内容を区別する必要がある場合は、元の指示を消さずに追記する。

`Status` の値は英語で記載する。各状態の意味と AI の作業範囲は次のとおり。

| Status | どういう状態か | AI がしてよい作業 |
| --- | --- | --- |
| `proposed`（提案中） | 要求や方針を検討しており、実装の承認はまだない。 | 調査・内容確認・レビューまで。ユーザーが明示的に承認するまで実装しない。 |
| `approved`（承認済み） | ユーザーが実装を承認し、着手できる状態。 | 指定されたタスクの範囲内で実装を開始できる。 |
| `in-progress`（作業中） | 実装・検証、または試験で見つかった問題の修正を進めている。 | 承認済みの範囲で実装・検証・修正を継続できる。 |
| `implemented`（実装済み） | 実装は済んでいるが、人手試験など必要な確認が残っている。 | 残っている検証を進め、結果を報告する。人手試験はユーザーの結果を待ち、確認前に完了と扱わない。 |
| `completed`（完了） | 必要な検証を終え、受け入れ条件を満たしている。 | 現在の実装を確認する。ユーザーが再開または追加変更を明示しない限り再実装しない。 |

AI は着手前に対象タスクの `Status` とユーザーの指示を確認し、上表に従って作業範囲を判断する。AI が自己判断で `proposed` を承認済みとみなして実装を開始してはいけない。

ユーザーから現在の依頼で明示された指示がある場合は、その指示を優先する。たとえば `proposed` のままでも「このタスクを実装してください」と明示された場合は実装の承認として扱う。「内容を確認してください」だけでは実装の承認とみなさない。

状態の判断と task 文書の更新は区別する。実装・修正を依頼された対象taskでは、実際の進捗や確認結果をStatus等へ反映する。AI自身の記載によって実装の承認を作り出してはいけない。未実施の試験を合格と推測して `completed` にしてはいけない。

これは AI が従う作業ルールであり、`Status` の値だけでファイル編集やコマンド実行を機械的に禁止する仕組みではない。

AIへ作業を依頼するときは対象ファイルを明示する。指定されていないタスクは実装対象に含めない。

完了後も有効な仕様、設計、運用手順は `README.md` または `docs/` に反映する。タスク文書は、その task に関する指示と実装後に確定した修正内容の記録であり、現在有効な仕様の唯一の根拠として扱わない。

## 既存の記録

旧 `.ai/workflows/` から移した既存文書は、実装時の依頼を記録するため、元のファイル名と内容のまま保持する。新規タスク向けの命名・記載形式へ遡及的に書き換えず、現在の実装や仕様はコード、テスト、`README.md` から確認する。

# Project-Specific Rules

このファイルは、本プロジェクト固有の技術構成、既存仕様、安全上の制約、検証方法を定める。

全プロジェクト共通の作業ルールは`.ai/common.md`を参照すること。

## 技術構成

本プロジェクトは、以下で構成される単一バイナリのWebアプリケーションである。

- Rust 2024
- Axum
- SQLite
- Google Calendar API

変更前に、対象となる処理の責務が以下のどこにあるかを確認する。

- ルートハンドラ
- HTML生成
- Google Calendar API呼び出し
- SQLite永続化
- 認証およびセッション管理
- 設定の読み込み

## 変更範囲

`src/main.rs`は複数の責務を含むため、リファクタリングは責務単位で小さく進める。

ビューを分離する場合は、HTML生成と表示用ヘルパーだけを対象とする。

明示的な要求がない限り、ビュー分離と同時に以下を再構成しない。

- ルーティング
- 認証
- Google Calendar API処理
- SQLite処理
- 設定の読み込み
- アプリケーション全体のモジュール構成

大規模な移動や削除を一度に行わず、小さな変更単位ごとにフォーマットチェックとコンパイル確認を行う。

## 自動リロード

ダッシュボードの自動リロード機能は意図して削除されている。

明示的な要求がない限り、以下を再導入しない。

- ページ更新タイマー
- 更新までのカウントダウン
- JavaScriptによる自動更新
- `window.location.reload()`を利用した定期更新
- 自動更新のための設定値やテンプレート引数

## 環境変数

環境変数を追加、変更、削除する場合は、以下を確認する。

- `src/main.rs`
- `.env.example`
- `docker-compose.yml`
- `README.md`

変数名、説明、許可値、デフォルト値について、必要な箇所を同期する。

ローカルの`.env`を変更対象またはコミット対象にしない。

## ローカルデータと認証情報

以下をコミットしない。

- `.env`
- OAuthトークン
- SQLite DB
- セッション情報
- Cookie
- 実運用データ
- その他のローカル設定や認証情報

`data/.gitkeep`以外の`data/`配下を変更対象にしない。

調査や検証を行う場合も、秘密値を出力、ログ、テスト結果、完了報告へ転載しない。

## SQLite

SQLiteの変更は、既存データを保持できる後方互換な方法を優先する。

明示的な依頼と事前確認なしに、以下を行わない。

- テーブルの削除
- 列の削除
- SQLite DBの再作成
- 実データの更新または削除
- 後方互換性のないスキーマ変更

スキーマを変更する場合は、既存データへの影響と移行方法を確認する。

## Google Calendar認証

Google CalendarのOAuth scopeは`calendar.readonly`を維持する。

明示的な要求なしに、OAuthの権限を追加または拡大しない。

以下を弱める変更を行わない。

- 認証
- Cookieの保護
- セッション管理
- リダイレクト先の検証
- OAuth stateなどの検証

## HTMLと外部入力

以下のような外部由来の値をHTMLへ埋め込む場合は、必ず`escape_html`または同等の処理を通す。

- Google Calendar APIから取得した値
- SQLiteから取得した値
- フォーム入力
- URLパラメーター
- 環境変数
- エラーメッセージ
- ユーザー名やカレンダー名

URLとリダイレクト先には、既存の検証・正規化処理を使用する。

認証や入力検証を回避するための独自処理を追加しない。

## 日時とタイムゾーン

日時表示とGoogle Calendarの取得範囲は`Asia/Tokyo`を前提とする。

明示的な要求なしに、タイムゾーンや日時解釈を変更しない。

日時処理を変更する場合は、日付境界、終日予定、タイムゾーン変換への影響を確認する。

## GOOGLE_MAX_RESULTS

`GOOGLE_MAX_RESULTS`の許可値は以下とする。

- `10`
- `20`
- `30`
- `40`

明示的な要求なしに、この許可値を変更しない。

`GOOGLE_MAX_RESULTS`は、以下の両方に適用される現行仕様を維持する。

1. カレンダーごとのGoogle Calendar API取得上限
2. 複数カレンダーを統合して時刻順に並べた後の最終表示上限

片方だけへ適用する仕様に変更しない。

## Rustコードの検証

Rustコードを変更した場合は、原則として以下を実行する。

```console
cargo fmt --check
cargo check
cargo test
git diff --check
```

検証が失敗した場合は、今回の変更による失敗か、変更前から存在する失敗かを切り分ける。

`cargo fmt --check`が既存の未整形箇所によって失敗する場合は、要求と無関係なコードを一括で整形しない。

変更を小さな単位に分けられる場合は、各単位で`cargo fmt --check`と`cargo check`を実行する。

## HTMLとフォームの検証

HTMLやフォームを変更した場合は、少なくとも以下を確認する。

- 主要なHTML要素が生成される
- 必要なリンクとフォームが生成される
- 外部由来の値がエスケープされる
- URLとリダイレクト先が検証される
- 認証あり・なしの分岐が維持される
- エラー時の表示が適切である

外部のGoogle OAuthが必要で確認できない経路は、確認済みとして扱わず、未確認事項として報告する。

実際の認証情報を外部環境へ送信して検証しない。

## コンテナの検証

`Dockerfile`または`docker-compose.yml`を変更した場合は、原則として以下を確認する。

1. Compose設定が正常に解決される
2. イメージをビルドできる
3. コンテナを起動できる
4. 起動ログに明らかなエラーがない
5. `GET /health`が正常なHTTP応答を返す

検証用のローカル環境と、本番環境または実運用中のコンテナを区別する。

明示的な依頼なしに、本番環境や実運用中のコンテナを起動、停止、再起動、更新しない。
